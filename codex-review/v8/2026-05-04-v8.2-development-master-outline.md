# V8.2 修订重构开发总纲

> 文档定位：
> 这不是新一轮“概念描述”，而是把 Claude 已经固定过的评审结论、`v8.1` 已经完成的工程收紧，以及当前仓库 `narrative_v8` 的真实 runtime 状态，压成一份可以继续开发、继续拆 PR、继续送审的 `V8.2` 开发总纲。
>
> 这份文档的职责只有三个：
> 1. 固化 `V8.2` 的唯一工程闭环
> 2. 明确哪些边界已经在文档层收紧，哪些边界还没有在 runtime 落地
> 3. 为后续执行清单、PR 切分和 Claude 复评提供统一总口径

## 0. 文档关系与适用范围

`V8.2` 不是推翻 `v8`，也不是否定 `v8.1`。

它的定位是：

1. `v8` 负责提出方向
2. Claude 评审负责指出“方向对，但工程边界太软”
3. `v8.1` 负责回答“该保留什么、该拆开什么、该先验证什么、该怎么调整顺序”
4. `V8.2` 负责把这些答案整理成一份真正可执行的开发需求说明包

因此本轮不再追加新的创意层内容，重点是把下面这条链路收成工程闭环：

`人格底盘 -> 合法性外壳 -> 心理缺口 -> 原语选择 -> 场景适配 -> 失手恢复 -> 升级触发 -> 状态迁移`

适用范围也必须继续锁死：

1. 仅限 `alpha-autopilot` 当前仓库
2. 仅限 `backend/app/services/narrative_v8/` 这一独立 increment 控制核心
3. 不直接改写 `v1/v2` baseline
4. 不直接接入 `writer`、UI、CLI、持久化、默认主链路
5. 不把评审文档反过来当需求扩写器

## 1. 为什么需要 V8.2，而不是继续停留在 v8.1

`v8.1` 已经做对了三件重要事情：

1. 把状态账本拆成 relationship / narrative / psychological / hook 四层
2. 把刀法约束、scene restrictions、observer requirements、fallback 形状、flavor 边界、helper 顺序、测试顺序都收紧了
3. 把 “controller 不能发现业务规则” 这件事说清楚了

但从“送去实现”这个标准看，`v8.1` 还有三个现实缺口没有被一份统一文档封死：

1. 它仍然主要是“回答评审问题”，还不是“完整开发需求说明”
2. `failure / recovery / upgrade / transition` 虽然已经被提升进设计，但还没有在当前 runtime 现实里被单独标成第一优先级补齐项
3. 当前仓库的 `narrative_v8` 已经存在部分 runtime 实现，如果不把“文档已收紧”和“代码仍未对齐”拆开写，后续 Claude 很容易继续抓“文档假装现实已完成”

所以 `V8.2` 的本质任务不是再写一版 schema，而是补上以下三种闭口：

1. `总纲闭口`
   把所有边界、顺序、责任和剩余风险放到一份上位总纲里
2. `执行闭口`
   把后续实现拆成明确 PR / 文件 / 门禁 / 测试顺序
3. `现实闭口`
   把“当前已经有哪些 runtime 模块”和“还差哪些结构性整改”单独标清

## 2. V8.2 的唯一工程主线

`V8.2` 只承认一条主线，不允许 controller 兜底补洞：

| 阶段 | 结构 owner | 输入 | 输出 | 不允许发生的事 |
|---|---|---|---|---|
| 人格底盘 | `VillainProfile` | 核心匮乏、时间尺度、禁手、稳定风味 | 稳定人格约束 | 运行时 flavor 反向定义角色 |
| 合法性外壳 | `public_mask` + `FlavorAxisProfile` | 对外姿态、见证人依赖、公开性倾向 | 本场外壳窗口 | 把“外壳”写成纯措辞修饰 |
| 心理缺口 | `TargetProfile` | need / fear / defense / witness sensitivity / identity anchor | 目标侧可被命中的缺口 | 用空泛 weak points 代替计算字段 |
| 原语选择 | `KnifePrimitive` + `KnifeConstraintSet` + `KnifeCompatibilityEdge` | 原语库、约束词表、兼容图 | 可筛选原语集合 | 用 `preferred_knives` 数组替代完整约束 |
| 场景适配 | `SceneContext` + `SceneObserver` + `PowerEdge` | visibility / observer topology / power topology / time pressure | 可执行场景窗口 | 把 audience 当成一组无角色对象 |
| 失手恢复 | `FailureMode` + `RecoveryMode` | 暴露、节奏丢失、位置锁死、解释权丢失 | 修复策略 | fallback 直接等于 collapse |
| 升级触发 | `UpgradeTrigger` + `UpgradePath` | 原语停滞、外壳被识破、更高阶路径出现 | 升级方向 | upgrade path 无 trigger 漂浮存在 |
| 状态迁移 | `TransitionLayer` + `LedgerSnapshot` + `StateLedgerShift` | prior state、选择结果、修复/升级信号 | next state + layered shift | controller 内联状态机推断 |

一句话约束：

`selector` 负责“先硬过滤，再对幸存项打分”。

`ledger / transition helpers` 负责“结构化更新状态”。

`controller` 只负责“编排已存在的规则结果”。

## 4. V8.2 必须新增或强拆的结构

### 4.1 状态账本必须继续保持四层，而不是退回 flat event log

`LedgerSnapshot` 与 `StateLedgerShift` 必须继续锁定四层：

1. `relationship`
2. `narrative`
3. `psychological`
4. `hook`

并继续坚持这三条边界：

1. `Snapshot` 表示当前局势，不表示事件流水
2. `Shift` 表示本次动作偏移，不表示长线状态本体
3. `hook` 层只管理伏笔、回收、延迟 payoff，不能和 relationship 层串写

### 4.2 刀法约束必须脱离 profile 数组，进入独立约束层

以下两层必须继续存在并成为 selector 前置输入：

1. `KnifeConstraintSet`
   - `scene_restrictions`
   - `target_restrictions`
   - `observer_requirements`
   - `anti_conditions`
   - `backfire_conditions`
   - `ineffective_conditions`
   - `flavor_conflicts`
2. `KnifeCompatibilityEdge`
   - `left`
   - `right`
   - `relation`
   - `reason`

约束分工必须写死：

1. `preferred_knives / secondary_knives / forbidden_moves`
   只表达“偏好与禁手”
2. `constraint set`
   表达“什么时候不能用、没效果、会反噬”
3. `compatibility graph`
   表达“刀和刀能不能连续使用、为什么不能”

### 4.3 场景模型必须继续把 observer / power topology 当一等结构

`SceneContext` 必须继续包含：

1. `observers`
2. `power_topology`

`SceneObserver.role` 必须固定区分：

1. `witness`
2. `judge`
3. `transmitter`
4. `buffer`
5. `recovery_node`

不能再退回“有几个人在场”的粗粒度 audience。

### 4.4 输出包必须拆成结构层，而不是 narrative summary

`VillainFeedbackPacket` 在 `V8.2` 必须以这 6 层为准：

1. `decision layer`
2. `explanation layer`
3. `transition layer`
4. `state shift layer`
5. `hook layer`
6. `flavor layer`

其中最关键的变化是：

`transition layer` 在 `V8.2` 不再是推荐项，而是必选项。

### 4.5 风味字段必须继续收口，不能重新散落

`V8.2` 只允许四个风味位置：

1. `stable preference`
   存在于 `FlavorAxisProfile`
2. `temporary shell`
   由 `public_mask` 与场景共同生成
3. `scene render`
   由 `render_flavor` 生成本场结构影响
4. `output flavor`
   存在于 `FlavorRender`

风味不允许重新漂到：

1. selector 的魔法分支里
2. controller 的手写说明文案里
3. 多个 packet 子层互相抢定义权里

### 4.6 Transition 必须从“设计意图”升级为“代码契约”

这是 `V8.2` 相比 `v8.1` 最重要的升级点。

以下结构必须进入 runtime 合同层，而不是只停留在文档里：

1. `ControlSurfaceState`
2. `FailureMode`
3. `RecoveryMode`
4. `UpgradeTrigger`
5. `UpgradePath`
6. `TransitionLayer`
7. `SceneContext.current_control_state`

并且必须满足：

1. `prior_state -> next_state` 是显式字段，不是解释文案里的暗示
2. `fallback` 只是本次没有稳定出刀，不等于自动 collapse
3. `collapsed` 不能同时被声明为“已经进入 recovery”
4. `upgrade_path` 不能脱离 `upgrade_trigger`
5. transition 推导必须由 helper 负责，不能在 controller 中散落

## 5. 前置验证是 V8.2 的强制门，不是建议门

`V8.2` 明确规定：controller 之前，至少要先有以下 7 类验证门。

1. `schema validation`
2. `knife compatibility validation`
3. `scene compatibility validation`
4. `state boundary validation`
5. `transition policy validation`
6. `differential validation`
7. `fallback validation`

每个验证门的职责必须写死：

### 5.1 Schema Validation

负责拦截：

1. profile 字段形状错误
2. public scene 无 observers
3. packet 仍然是旧式扁平 payload
4. fallback packet 假装自己选中了刀
5. transition layer 缺字段或自相矛盾

### 5.2 Knife Compatibility Validation

负责拦截：

1. incompatible edge 未生效
2. conditional edge 无解释
3. incompatible knife 仍进入 selected pool

### 5.3 Scene Compatibility Validation

负责拦截：

1. observer requirement 缺失
2. scene restriction 不满足
3. power topology 不支持却仍允许落刀

### 5.4 State Boundary Validation

负责拦截：

1. relationship / narrative / psychological / hook 串写
2. hook recovery 覆盖其他层
3. 单次 shift 高幅度跨层失控

### 5.5 Transition Policy Validation

负责拦截：

1. `current_control_state` 缺失却仍尝试派生 transition
2. `upgrade_path` 无 `upgrade_trigger`
3. `collapse` 被假装成 `recovery`
4. `prior_state` / `next_state` 不可追溯

### 5.6 Differential Validation

必须覆盖：

1. same knife / different villain
2. same villain / different scene
3. observer topology 变化影响 public-pressure fit
4. flavor 差异影响结构，不只是措辞

### 5.7 Fallback Validation

必须覆盖：

1. no-fit 时真的进入 `fallback`
2. `selected_signals` 必须为空
3. `primary_knife_id` / `secondary_knife_id` 必须为空
4. `fallback_action` / `fallback_reason` 必须显式给出

## 6. Helper 优先于 Controller，是 V8.2 的硬约束

以下 helper 必须先做，且必须有明确 owner：

1. `build_candidate_knife_ids`
2. `evaluate_knife_rejection`
3. `evaluate_compatibility_conflict`
4. `select_knives`
5. `render_flavor`
6. `build_state_shift`
7. `apply_state_shift`
8. `derive_transition_outcome`
9. `build_risk_if_exposed`
10. `build_hook_seed`
11. `build_external_move_envelope`

controller 不允许承担以下职责：

1. 推断 forbidden move 是否生效
2. 推断 observer requirement 是否满足
3. 推断 anti-condition / backfire / ineffective condition
4. 计算 knife-to-knife incompatibility
5. 决定 fallback 是否成立
6. 内联 state shift 规则
7. 内联 failure / recovery / upgrade / collapse 状态机

如果某条规则只能在 controller 里写出来，说明 helper 边界还没收紧到位。

## 7. 当前 runtime 现实必须和文档现实分开写

截至 `2026-05-05`，当前仓库现实不是“完全未实现”，也不是“已经实现完毕”。

### 7.1 已经存在的 runtime 模块

`backend/app/services/narrative_v8/` 当前已经存在：

1. `schemas.py`
2. `constraints.py`
3. `knife_library.py`
4. `selection.py`
5. `flavor.py`
6. `ledger.py`
7. `transitions.py`
8. `controller.py`
9. `__init__.py`

同时已经存在：

1. `tests/test_narrative_v8_schemas.py`
2. `tests/test_narrative_v8_knife_library.py`
3. `tests/test_narrative_v8_selection.py`
4. `tests/test_narrative_v8_flavor.py`
5. `tests/test_narrative_v8_ledger.py`
6. `tests/test_narrative_v8_transitions.py`
7. `tests/test_narrative_v8_controller.py`
8. `tests/test_narrative_v8_integration.py`
9. `tests/test_run_v8_acceptance_review.py`

### 7.2 已在 runtime 部分落地的内容

以下边界已经在 runtime 层有明显落地：

1. 分层 ledger
2. constraint set 与 compatibility graph
3. observer topology 与 power topology
4. structured fallback shape
5. flavor render 的 structural targets
6. `SceneContext.current_control_state`
7. schema 内的 `TransitionLayer`
8. `VillainFeedbackPacket.transition` 子层
9. helper-owned `transitions.py`
10. controller 对 `build_explanation` / `build_future_hooks` / `build_state_shift` / `derive_transition_outcome` 的委托
11. 独立 transition tests，以及 controller / integration 对 transition 的回归断言

### 7.3 仍未完全收紧的关键缺口

当前 runtime 已经补上 transition ownership 的主结构，但仍然还有下面这些“不能假装已经彻底完成”的残余缺口：

1. `derive_transition_outcome` 现在是第一版确定性状态机，阈值与分支仍偏启发式，还不是可配置 policy layer
2. `transition.next_state` 现在已经通过 `BuildVillainFeedbackOutput.next_control_state` 显式承接，但上层调用方是否统一采用这条接口仍需继续守门
3. controller 已经不再拥有 `_build_state_shift`、`_build_future_hooks`、`_build_explanation`，但它仍然是组包中枢，后续开发如果缺少守门测试，规则有漂回来的风险
4. fallback 现在已经同时进入 `decision` 与 `transition` 的边界表达，但 fallback policy 仍分散在 selection helper 与 transition helper 之间，而不是单独模块化
5. explanation / flavor / transition 的边界虽然已经拆开，但 flavor 信号仍参与 transition 派生，后续如果不守住 owner，很容易再次把“文案风味”偷带回状态判断

这意味着：

`V8.2` 现在可以诚实描述成“transition runtime 已经落地，controller 已经明显瘦身，控制面状态也已有显式承接出口，但 transition 阈值、上层采用一致性、以及 helper 边界回退风险仍需继续盯防”。

## 8. V8.2 的实施顺序必须锁死

实施顺序继续以这条链为准：

1. `schema definition`
2. `constraint and compatibility rules`
3. `validation layer`
4. `knife library`
5. `selection helpers`
6. `flavor rendering`
7. `layered ledger application`
8. `transition state machine`
9. `controller orchestration`

注意：

`transition state machine` 在 `V8.2` 必须从“ledger 旁支”升级为单独步骤，不能继续埋在 ledger 或 controller 后面。

## 9. V8.2 的测试顺序必须锁死

测试顺序继续以这条链为准：

1. `schema tests`
2. `compatibility tests`
3. `state boundary tests`
4. `transition state tests`
5. `differential tests`
6. `fallback tests`
7. `controller integration tests`

即使 transition tests 已经独立存在，也不能跳过前面的 schema / compatibility / state boundary 门，直接把 controller 当成主验证入口。

## 10. V8.2 的完成定义

只有同时满足以下条件，`V8.2` 才能被认为完成：

1. 总纲已经固化唯一闭环和唯一边界
2. 执行清单已经明确到真实文件、真实门禁、真实测试顺序
3. 当前 runtime 的“已实现 / 未实现”差异已经单独写清
4. `transitions.py`、`tests/test_narrative_v8_transitions.py`、`current_control_state`、`TransitionLayer` 已经在 runtime 与文档中双侧对齐
5. controller 的禁止职责已经写成可审计列表，并有回归测试守门
6. Claude 可以只看 `V8.2` 包，就知道哪些结构已经落地、哪些风险仍需继续追

## 11. 仍然保留的风险

即使 `V8.2` 完成，下面这些风险仍然不能假装已经消失：

1. 所有角色仍可能坍缩成同一个 smart-bad voice
2. flavor 仍可能退化成文案层修饰
3. layered ledger 仍可能被后续开发重新拍扁成 event log
4. scene 词表仍可能过粗，导致 selector 失真
5. recovery / upgrade / collapse 的阈值目前仍是第一版启发式，仍可能写得太软
6. `next_control_state` 仍可能在上层 orchestration 中无人采用
7. explanation layer 仍可能偷偷重新承担规则推断职责

当前缓解方式只有：

1. 差异化测试
2. helper-owned rule boundaries
3. transition 独立测试
4. controller 禁止职责清单

## 12. 一句话总纲

`V8.2` 的目标不是继续堆字段，而是把这套系统真正收成：

`人格底盘 -> 合法性外壳 -> 心理缺口 -> 原语选择 -> 场景适配 -> 失手恢复 -> 升级触发 -> 状态迁移`

的完整工程闭环，并且让 Claude 能够逐项验证：

1. 边界是否已经显式
2. 规则是否已经前置
3. helper 是否已经接住责任
4. controller 是否已经瘦身
5. runtime 与文档是否已经对齐
