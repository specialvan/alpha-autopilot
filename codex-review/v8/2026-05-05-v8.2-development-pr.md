# V8.2 开发需求 PR 文档

> 目标：
> 这份文档不是讨论方向，也不是继续扩写概念，而是把当前 `narrative_v8` 的真实 runtime 状态、Claude 已固定的评审证据、以及 `V8.2` 的收口要求，整理成一份可以直接交给 Codex 执行开发计划的 PR 级需求说明。
>
> 定位：
> - 这是 **开发需求**，不是新功能提案
> - 这是 **执行边界**，不是创意发挥
> - 这是 **对齐说明**，不是代码实现
> - 这是 **审计留痕**，不是“看起来差不多”的口头总结

## 1. PR 背景

当前仓库里的 `backend/app/services/narrative_v8/` 已经具备一部分 runtime 实现，包括：

- schema
- constraints
- knife library
- selection
- flavor
- ledger
- controller
- 相关测试

但根据 Claude 的上一轮评审，以及后续基于证据的结构化拆解，最关键的一层已经补齐到 runtime：

> **transition ownership 已经独立成 schema + helper + tests，controller 也已经明显退回 orchestrator。**

因此，`V8.2` 当前要做的，不是再重复声明“缺 transition”，而是把现有 runtime 改造成一个真正可继续开发、可验证、可回退、并且对残余风险说真话的工程版本。

## 2. 本 PR 的核心判断

### 2.1 当前状态

当前实现已经对齐了大部分 v8.1 收紧成果，尤其是：

- 刀法约束不是纯偏好数组了
- 场景模型已经有 observer topology 和 power topology
- ledger 已经是四层结构
- selection 已经有硬过滤和兼容判断
- flavor 已经不再只是纯文案

### 2.2 本次收口前的关键缺口

在 `2026-05-07` 这轮收口前，仍有这些问题没有完全收口：

1. transition state machine 已经提炼出显式 policy signals + rule order，并进一步收紧成 topology-gated upgrade rules；同时 benchmark breadth 已补到 workbench preview 的 public-network upgrade / low-exposure upgrade / private-recovery fallback / public collapse / disabled rollback 五类样本，但更广的 coverage 仍有限
2. `BuildVillainFeedbackOutput.next_control_state` 已经作为控制面承接出口落地，`BuildVillainFeedbackOutput.build_followup_scene(...)` 也已经把 standalone runtime 的采用路径固定下来，`v2` workbench contexts 也已通过 `v8_preview` 接上这条接口，但更广的上层调用方仍需继续守门
3. controller 虽然已经迁出 `_build_state_shift` / `_build_future_hooks` / `_build_explanation`，但仍然是组包中枢，后续存在边界回退风险
4. flavor 信号参与 transition 派生，这条边界如果没人守测试，仍可能重新软化

所以本 PR 的核心工作是：

> **把这些尾项全部落成审计事实、显式 payload 与回归门，而不是继续留在“后续守门项”的口头描述里。**

---

## 3. PR 目标

本 PR 的目标只有一个：

> **把 `V8.2` 变成一份真正可执行、可验证、可回退的开发需求基线。**

具体要求：

1. 先把 schema 和边界锁死
2. 再把 constraint 与 selector 的硬过滤补齐
3. 再把 transition 作为独立 state machine helper 守住边界
4. 最后继续盯住 controller，不让规则漂回 orchestrator

---

## 4. 设计原则

### 4.1 先收边界，再写行为

任何规则如果只能在 controller 里靠分支写出来，说明边界还没收紧。

### 4.2 transition 必须是一等结构

transition 不是 explanation 文案，也不是 ledger 的附属注释。

它必须是：

- schema 可见
- helper 可调用
- test 可独立覆盖
- packet 可显式输出

### 4.3 controller 必须退回 orchestrator

controller 只做编排，不发现规则。

禁止它承担：

- forbidden move 判断
- observer requirement 判断
- compatibility 冲突判断
- transition state machine 推断
- fallback 语义发明
- ledger cross-layer rule 组装

### 4.4 runtime 必须诚实

文档必须继续明确：

- 哪些内容已经在 runtime 里
- 哪些内容已经落地到 runtime
- 哪些内容仍然只是文档边界
- 哪些内容是 v8.2 的残余守门项

不能再把“尚未完成”写成“已经完成”。

## 6. 必须保留或继续守门的结构

### 6.1 Schema 层

必须已经具备并继续保留：

- `ControlSurfaceState`
- `FailureMode`
- `RecoveryMode`
- `UpgradeTrigger`
- `UpgradePath`
- `TransitionLayer`

必须在 `SceneContext` 中显式保留：

- `current_control_state`

必须在 `VillainFeedbackPacket` 中显式保留：

- `transition`

### 6.2 Transition Layer 的职责

`TransitionLayer` 必须显式表达：

- prior state
- next state
- failure mode
- recovery mode
- upgrade trigger
- upgrade path
- collapse / fallback 边界

并且必须满足：

- `fallback != collapse`
- `upgrade_path` 不能脱离 `upgrade_trigger`
- `collapsed` 不能同时携带 active `recovery_mode`

### 6.3 独立 transition helper

必须存在：

- `backend/app/services/narrative_v8/transitions.py`

至少包含：

- `derive_transition_outcome`
- 其他用于 transition 状态机的辅助函数

同时必须明确：

- `build_state_shift` 归 `ledger.py` 所有
- `transitions.py` 不负责 ledger 分层写入

### 6.4 独立 transition tests

必须存在：

- `tests/test_narrative_v8_transitions.py`

并独立覆盖：

- `harmless -> suspicious`
- `suspicious -> repair_attempt`
- `repair_attempt -> partially_restored`
- `suspicious -> upgraded`
- `suspicious -> collapsed`
- `fallback != collapse`
- `upgrade` 与 `recovery` 不能同时成为主结果
- hook recovery 不能覆盖其他 ledger 层

## 7. 约束与验证要求

### 7.1 Schema validation

必须先验证：

- transition 字段是否完整
- `current_control_state` 是否存在
- fallback / collapse / upgrade 约束是否一致
- packet 是否仍然保留旧式扁平结构

### 7.2 Knife compatibility validation

必须验证：

- `forbidden_moves` 是硬拒绝，不是低分项
- `observer_requirements` 缺失时是硬拒绝
- `anti_conditions` / `backfire_conditions` / `ineffective_conditions` 不被压扁成简单分数
- incompatible knife 不进入 scored pool

### 7.3 Scene compatibility validation

必须验证：

- 当前场景是否支持该外壳
- 当前场景是否支持该刀法
- 当前 observer topology 是否满足要求
- 当前 power topology 是否允许推进

### 7.4 State boundary validation

必须验证：

- relationship / narrative / psychological / hook 不串写
- 单次 shift 不越界
- hook recovery 不覆盖其他层

### 7.5 Transition policy validation

必须验证：

- transition 派生依赖 `current_control_state`
- `upgrade_path` 必须有 `upgrade_trigger`
- `collapsed` 不能同时被标成 `recovery`
- `prior_state` / `next_state` 可以追溯

---

## 8. 实施顺序

后续开发必须按以下顺序推进：

1. `schema definition`
2. `constraint and compatibility rules`
3. `validation layer`
4. `knife library`
5. `selection helpers`
6. `flavor rendering`
7. `layered ledger application`
8. `transition state machine`
9. `controller orchestration`

注意：

- `transition state machine` 必须独立于 ledger 和 controller
- controller 不得反过来发现 transition 规则

---

## 9. 测试顺序

后续测试必须按以下顺序推进：

1. `schema tests`
2. `compatibility tests`
3. `state boundary tests`
4. `transition state tests`
5. `differential tests`
6. `fallback tests`
7. `controller integration tests`

测试重点：

- same knife / different villain
- same villain / different scene
- same scene / different shell
- fallback 结构诚实性
- transition 独立性

## 12. 风险说明

即使完成本 PR，仍然保留这些风险：

1. 所有角色坍缩成同一个 smart-bad voice
2. flavor 退化成纯文案层
3. ledger 被重新拍扁成 event log
4. scene 过粗导致 selector 失真
5. workbench-only 以外的 rollout 仍未开启，但这属于故意保持 scope，而不是当前 V8 core 的 benchmark 缺口
6. `next_control_state` / `followup_scene` 已在当前允许的 workbench consumer 中闭合，更广的 API / UI / writer 采用继续保持 out of scope
7. explanation layer / controller 边界仍需要长期测试守门，但当前 PR 指向的 delegate 回退风险已经并入显式 regression gate

因此本次收口的目标不是“把所有创作风险归零”，而是“把 original PR 指向的 benchmark、adoption、controller 三类工程尾项全部折进代码和测试”。
