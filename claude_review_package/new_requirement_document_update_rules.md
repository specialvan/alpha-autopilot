# 新需求文档更新规则

## 1. 目的

这份规则用于判断新需求出现时，哪些文档必须更新，哪些文档只需要局部补充，哪些文档需要重新收敛。

核心目标有三个：

- 不重复重写所有文档
- 不让局部文档反向覆盖主线定义
- 不让文档之间出现互相打架的口径

## 2. 总原则

### 2.1 先判层级，再决定改哪些文档

任何新需求先判断属于哪一层：

- **Baseline**：影响 `v1/v2` 稳定基线的变更
- **Increment**：影响 `v3` 增量层的变更
- **Experimental**：独立验证，不直接影响主线默认行为

### 2.2 文档优先级

文档发生冲突时，按以下顺序裁决：

1. `CODEX_DEVELOPMENT_GOVERNANCE.md`
2. `execution_governance.md`
3. `new_requirement_execution_flow.md`
4. `new_requirement_intake_template.md`
5. `task_launch_template.md`
6. `new_requirement_document_update_rules.md`
7. `PROJECT_STATUS.md`、`V2/frontend_PROJECT_STATUS.md`、阶段任务文档
8. `*_REVIEW_*`、历史说明、归档材料

### 2.3 裁决原则

- 上位治理文档优先
- 主线定义优先
- 保守解释优先
- 无法一致解释时，先冻结执行，再补充裁决记录

## 3. 什么时候只更新局部文档

如果新需求满足以下条件，通常只更新局部文档：

- 归属明确的 `Increment` 层
- 不改变主线定义
- 不影响 `v1/v2` 基线
- 不改变接口契约
- 不改变治理结构

### 典型局部更新项

- `PROJECT_STATUS.md`
- `V2/frontend_PROJECT_STATUS.md`
- 对应阶段任务文档
- 对应增量说明文档

## 4. 什么时候需要更新阶段文档

如果新需求满足以下任一条件，就要更新阶段相关文档：

- 影响 `v3` 的范围
- 需要新增阶段任务
- 需要调整增量优先级
- 需要补充评估、回滚、门禁说明

### 典型阶段文档

- `THIRD_PHASE_ROADMAP.md`
- `THIRD_PHASE_TASKS.md`
- `PROJECT_STATUS.md`
- `V2/frontend_PROJECT_STATUS.md`
- `V2/TECH_BOTTLENECKS.md`

## 5. 什么时候需要重收敛主线文档

如果新需求满足以下任一条件，就必须重收敛主线文档：

- 主目标发生变化
- `v2` 与 `v3` 的关系需要重写
- 出现新的长期主线
- `Baseline / Increment / Experimental` 定义需要调整
- Codex 执行顺序或治理规则需要调整
- 现有文档口径已经失效

### 典型主线文档

- `CODEX_DEVELOPMENT_GOVERNANCE.md`
- `MASTER_ROADMAP.md`
- `README.md`
- `README_FOR_CODEX.md`
- `codex_run_card.md`
- `final_document_index.md`
- `package_manifest.md`

## 6. 什么时候需要新增实验文档

如果需求还不稳定、还没收敛、还需要验证方案，就应该先落到实验层：

- 新建实验说明文档
- 新建实验结果记录
- 不直接改主线定义

## 7. 什么时候需要归档

当文档已经被新主线覆盖，或者其中的口径已经过时，就应该进入归档层：

- 旧评审报告
- 旧交付说明
- 过时路线图
- 已失效的阶段口径

## 8. 冲突处理规则

如果发现文档之间存在冲突，按下面顺序处理：

1. 先找治理文档
2. 再找执行流程文档
3. 再找接入模板和任务模板
4. 再看状态文档与阶段任务
5. 最后看评审和历史材料

### 冲突解决结果必须写明

- 冲突来源
- 裁决依据
- 裁决结果
- 受影响文档
- 是否需要补充回滚或门禁说明

## 9. 更新策略

### 小改动

只更新：

- 状态文档
- 局部任务文档

### 中改动

更新：

- 状态文档
- 阶段任务文档
- 增量说明文档

### 大改动

重收敛：

- 治理规范
- 总路线图
- Codex 执行说明
- 主线索引
- 文档清单

## 10. 长期维护原则

长期维护依赖四件事一起工作：

1. 文档治理：定义边界、层级和责任
2. 代码治理：模块分层、接口稳定、可回滚
3. 测试治理：回归集、验收集、门禁测试
4. 执行治理：按规则推进，不跳步

文档的作用是让这四件事始终对齐，不让新增需求把已有口径冲散。

## 11. 一句话总结

> 新需求先判层级，再看影响面；不改主线只改局部，改主线就重收敛；有冲突先按治理文档裁决，再更新执行文档。
