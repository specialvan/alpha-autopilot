# 新增需求时的文档更新规则

## 1. 目的

当 `alpha-autopilot` 出现新的功能需求时，用这份规则判断：

- 需不需要重写总纲
- 需不需要更新阶段文档
- 需不需要更新状态文档
- 需不需要新增实验文档
- 需不需要进入归档

目标是避免每次新增需求都把所有文档重做一遍，同时确保主线边界始终清晰。

## 2. 总原则

### 2.1 先分层，再决定改哪些文档

任何新需求先判断属于哪一层：

- **Baseline**：影响 `v1/v2` 稳定基线的变更
- **Increment**：影响 `v3` 增量层的变更
- **Experimental**：实验探索，不直接影响主线默认行为

### 2.2 只有改变主线边界时，才重收敛总纲

如果新需求会改变以下内容，就要重新检查总纲类文档：

- 主目标
- 阶段定义
- 层级归属
- `v2` / `v3` 关系
- 前端 / 后端职责边界
- schema / 接口契约

如果不影响这些边界，通常只更新局部文档。

## 3. 新需求的判断流程

### Step 1 判断层级

先问：

- 这是稳定基线修复吗？
- 这是 `v3` 增量能力吗？
- 这是实验探索吗？

### Step 2 判断影响面

再问：

- 是否会改主线目标？
- 是否会改阶段定义？
- 是否会改状态口径？
- 是否会改接口或 schema？
- 是否会让 `v3` 看起来像新主线？

### Step 3 决定更新哪些文档

根据影响面，选择局部更新、阶段更新或总纲更新。

## 4. 只需要局部更新的情况

满足以下条件时，一般只更新局部文档：

- 功能属于明确的 `Increment` 层
- 不改变主线定义
- 不改变 `v1/v2` 基线
- 不改接口契约
- 不改治理结构

### 典型需要更新的文档

- `PROJECT_STATUS.md`
- `frontend_PROJECT_STATUS.md`
- 对应阶段任务文档
- 对应 `Increment` 说明文档

## 5. 需要阶段级更新的情况

满足以下任一情况时，要更新阶段相关文档：

- 新功能影响 `v3` 的范围
- 新功能需要新增阶段任务
- 新功能改变增量层的优先级
- 新功能补充评估、回滚、门禁规则

### 典型需要更新的文档

- `THIRD_PHASE_ROADMAP.md`
- `THIRD_PHASE_TASKS.md`
- `PROJECT_STATUS.md`
- `frontend_PROJECT_STATUS.md`
- `TECH_BOTTLENECKS.md`

## 6. 需要总纲级更新的情况

如果新需求满足以下任一条件，就要重新收敛总纲类文档：

- 主目标发生变化
- `v2` 与 `v3` 的关系要重写
- 新增一个新的长期主线
- 需要调整 `Baseline / Increment / Experimental` 定义
- 需要调整 Codex 执行顺序或治理规则
- 新需求会让已有文档口径失效

### 典型需要更新的文档

- `CODEX_DEVELOPMENT_GOVERNANCE.md`
- `MASTER_ROADMAP.md`
- `README.md`
- `claude_review_package/README_FOR_CODEX.md`
- `claude_review_package/codex_run_card.md`
- `claude_review_package/final_document_index.md`
- `claude_review_package/package_manifest.md`

## 7. 需要新增实验文档的情况

如果需求还不稳定、还没冻结、还需要验证方案，就应该先放到实验层：

- 新建实验说明文档
- 新建实验结果记录
- 不要直接改主线文档

## 8. 需要归档的情况

当文档已被新总纲覆盖，或者其中的口径已经过时，应进入归档层：

- 旧评审报告
- 旧交付说明
- 过时路线图
- 已失效的阶段口径

## 9. 维护策略

### 小改动

只更新：
- 状态文档
- 局部任务文档

### 中改动

更新：
- 状态文档
- 阶段任务文档
- 增量说明文档

### 大改动

重收敛：
- 治理规范
- 总路线图
- Codex 执行说明
- 主线索引
- 文档清单

## 10. 长期维护是不是靠这些文档实现

### 结论

**是，但不只是靠文档。**

长期维护通常靠四件事一起工作：

1. **文档治理**：定义边界、层级、责任
2. **代码治理**：模块分层、接口稳定、可回滚
3. **测试治理**：回归集、评估集、门禁测试
4. **执行治理**：Codex / 开发流程按规则推进

文档的作用是让这四件事始终对齐，不让系统随着新增需求慢慢漂掉。

## 11. 一句话总结

> 新需求先判层级，再看影响面；不改主线只改局部，改主线就重收敛总纲。
