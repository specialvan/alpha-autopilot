# 测试治理说明

## 1. 目的

测试治理用于判断代码改动是否真正可用，是否破坏了基线，是否满足新增需求的验收标准。

## 2. 测试分层

### 2.1 单元测试

用于验证单个函数、类或模块的局部逻辑。

适用场景：
- 纯逻辑函数
- 数据转换
- 评分、排序、规则判断
- 小范围边界条件

目标：
- 快速发现回归
- 保证基础逻辑稳定

### 2.2 集成测试

用于验证多个模块之间的协作是否正常。

适用场景：
- API 与服务层联动
- 前后端联动
- 推荐、训练、反馈闭环
- 质量层与主链路接入

目标：
- 验证系统链路可运行
- 发现模块接口不一致问题

### 2.3 回归测试

用于验证旧功能在新改动后是否仍然正常。

适用场景：
- 基线功能不允许被新功能破坏
- `v2` 稳定路径
- `v3` 增量接入后的默认行为

目标：
- 防止新需求污染旧能力
- 保证稳定收口

### 2.4 验收测试

用于验证某个需求是否真正达到了预期。

适用场景：
- 新增功能上线前
- 阶段性交付验收
- 增量层进入主线候选前

目标：
- 判断需求是否完成
- 判断是否可进入下一阶段

## 3. 测试门禁

### 3.1 新增功能最少要求

每次新增功能至少应满足：
- 有对应单元测试
- 如涉及跨模块协作，应有集成测试
- 如影响主线行为，应有回归测试
- 如属于需求交付，应有验收标准

### 3.2 主线变更要求

如果改动会影响 `Baseline`：
- 必须补回归测试
- 必须确认默认路径不变
- 必须说明回滚方式

### 3.3 增量接入要求

如果改动属于 `Increment`：
- 必须有对照测试
- 必须有增量前后差异说明
- 必须确认主线可关闭、可降级

## 4. 测试执行原则

- 先测最小范围，再测链路
- 先测本地可重复结果，再测复杂场景
- 先保证旧功能不坏，再验证新功能有效
- 测试失败时优先定位问题，不要用大改掩盖

## 5. 推荐的测试策略

### 5.1 小改动

- 单元测试 + 必要回归测试

### 5.2 中等改动

- 单元测试 + 集成测试 + 回归测试

### 5.3 大改动

- 单元测试 + 集成测试 + 回归测试 + 验收测试

## 6. 当前项目建议

对于 `alpha-autopilot`，建议重点维护以下测试方向：

- 推荐评分与排序
- `StoryState` / `CharacterState` 数据结构
- 训练与反馈链路
- `v2` workbench 接口
- `v3` decomposition / QC / projection 接入
- 前端路由和页面渲染

## 7. 一句话原则

> 测试治理的目标不是把测试写多，而是确保每一次改动都能被证明没有破坏基线，并且真的满足新增需求。
