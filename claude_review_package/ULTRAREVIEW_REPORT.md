# alpha-autopilot Ultrareview 评审报告

> 评审对象：`D:\workspace\alpha-autopilot`
>
> 评审目标：从架构完整性、实现质量、测试覆盖、产品可演进性、风险与下一步落地五个维度，给 Codex 提供一版可执行的综合评审结论。

## 1. 结论摘要

`alpha-autopilot` 已经从“单点原型”推进到“具备可验证链路的叙事推荐研究平台”，当前最大的价值不再是某个单独算法，而是它已经形成了一个较完整的闭环：

- 叙事状态建模
- 特征矩阵与版本管理
- 候选生成与排序
- 训练与反馈更新
- API 暴露与前端工作台
- `v3` 的逆向拆解 / quality layer 实验链路

从评审角度看，这个项目的核心优势是**结构清晰、可解释性强、实验链路完整**；核心短板是**质量层与主链路之间仍然存在明显“实验隔离”**，尚未形成统一的生产化评估与接入机制。

综合评价：**8.0 / 10**。

---

## 2. 项目现状判断

### 2.1 已完成的关键能力

根据仓库状态与项目文档，当前已具备以下能力：

- `StoryState` / `CharacterState` 等叙事状态抽象
- 基于特征矩阵的评分、更新与版本管理
- 候选生成、排序、训练循环与训练日志
- `FastAPI` demo API 与 dashboard preview
- 独立的 `V2 Workbench` 前端工作台
- `V3` taxonomy / schema / heuristic decomposition pipeline
- `PlotPilot` report 导入与 `reverse_outline_records` 生成
- `matrix_projection.json` 的本地构建能力

这些能力说明项目已经不是一个“只有 demo 的概念验证”，而是一个**可持续迭代的研究型系统**。

### 2.2 当前阶段定位

更准确地说，项目现在处于以下阶段：

1. **主链路已成型**：推荐、训练、展示、测试基本完整。
2. **质量层已启动**：`V3` 具备拆解、证据跨度、checkpoint、admission 分级。
3. **生产化仍未完成**：质量层尚未真正接入主训练与主推荐链路。

## 3. 架构评审

### 3.1 优点

#### 3.1.1 分层清晰

从仓库结构看，系统被拆分为：

- 核心推荐引擎
- narrative / feature / planner / trainer 等业务层
- API 层
- 前端工作台层
- `v2` / `v3` 实验层

这种拆分有利于后续把“推荐核心”与“质量判断层”分别演进。

#### 3.1.2 可解释性较强

项目整体明显偏向可解释路线，而不是端到端黑盒：

- feature matrix 便于审查
- versioning / training log 便于追溯
- heuristic decomposition 便于说明每个判断的依据
- evidence span / checkpoint 便于做人工复核

这对叙事类产品尤其重要，因为这类系统往往需要“为什么推荐这个章节”的解释能力。

#### 3.1.3 实验资产沉淀较好

项目并没有只停留在代码层，还沉淀了：

- `PROJECT_STATUS.md`
- `THIRD_PHASE_ROADMAP.md`
- 多份 delivery report / review report
- `docs/superpowers` 下的 design / plan 文档
- 测试资产与导入脚本

这意味着项目具备一定的工程治理能力，而不是纯手工试验。

### 3.2 问题

#### 3.2.1 主链路和质量层仍是“双系统”

`V3` 的拆解结果、style DNA、checkpoint、admission 分级虽然已经可用，但尚未正式进入现有训练/推荐主链路。

这会带来两个问题：

- 主系统无法直接受益于质量层判断
- 质量层结果不能自然反哺排序与训练

也就是说，当前更像是“并行实验成功”，而不是“架构统一成功”。

#### 3.2.2 数据接入仍偏夹具化

文档里已经明确提到：

- `mapped_chapter` 目前优先使用后端聚合上下文与导入夹具
- 还不是完整真实章节 API

这意味着数据链路仍然存在“样本驱动”痕迹，真实场景的稳定性、异常处理与规模化能力还没有被充分验证。

#### 3.2.3 质量评估仍缺统一尺度

当前虽然有测试通过率和本地构建成功信息，但缺少一套更统一的质量指标体系，例如：

- 推荐质量的离线指标
- 拆解质量的准确性指标
- 证据跨度与 checkpoint 的一致性指标
- admission 分级的误判分析

没有统一尺度，就很难判断 `V3` 是否真的提升了主链路质量。

## 4. 代码与工程质量评审

### 4.1 优点

- 代码组织总体健康，模块职责比较明确
- 单元测试与集成测试已有较广覆盖
- 前端与后端分离明确
- 项目状态文档较完整，便于交接与继续开发

### 4.2 风险点

#### 4.2.1 实验代码膨胀风险

仓库中实验文档、导入脚本、测试资产和多个阶段性产物很多，如果继续增加，容易出现：

- 入口不清晰
- 重复逻辑增多
- 评审难度上升
- “旧实验影响新主链路”的维护成本

#### 4.2.2 测试容易碎片化

当前测试覆盖面不错，但随着 `v2`、`v3`、workbench、导入脚本继续扩展，测试可能会从“保障核心”变成“维护成本”。

建议后续把测试分成：

- 核心推荐回归
- 质量层回归
- API contract tests
- 前端组件 / page tests
- 导入脚本 sanity tests

这样可以避免测试集过度耦合。

#### 4.2.3 配置与数据敏感项管理要更严格

仓库中可见 `.env`、测试样本、导入资产等相关痕迹。虽然这是研发阶段正常现象，但一旦向外分享或长期协作，必须明确：

- 哪些是可提交样本
- 哪些是本地私有环境变量
- 哪些是可再现 fixtures
- 哪些绝不能进主分支

## 5. 产品视角评审

### 5.1 项目已经具备的产品雏形

从用户角度看，它已经能提供：

- narrative recommendation 预览
- workbench 交互式上下文查看
- feature / state / plan 的可解释展示
- 质量层分析结果

这说明产品雏形已经出现，不再只是底层算法代码。

### 5.2 仍缺的产品关键点

#### 5.2.1 明确的用户角色

目前更像是“研究员 / 开发者友好”，尚未明确：

- 作者
- 编辑
- 运营
- 分析人员

各角色需要看什么、操作什么、关注什么指标，还不够清楚。

#### 5.2.2 闭环反馈机制

推荐系统真正的价值在于反馈闭环。当前已有训练与日志，但还缺少更明确的：

- 人工标注入口
- 决策回看入口
- 错误案例归档
- 线上反馈采样机制

#### 5.2.3 生产环境的解释与审计

对于叙事推荐系统来说，推荐结果必须可审计。建议以后统一输出：

- 输入上下文摘要
- 候选集
- 排序理由
- 质量层判断
- 最终推荐原因

现在这些能力已有雏形，但还未标准化。

## 6. `V3` 质量层专项评审

### 6.1 亮点

`V3` 是当前最值得继续投入的方向，因为它解决的是“如何把叙事拆解得更可靠”的问题。亮点包括：

- taxonomy / schema 先行
- chapter function / style DNA / checkpoint 结构化
- heuristic decomposition pipeline 可执行
- evidence span 支持审查
- admission 分级利于过滤
- PlotPilot report 导入说明它具备真实资产迁移能力

### 6.2 主要不足

- 仍是启发式，不是最终判定器
- 没有和主推荐链路统一
- 缺少 corpus-level QC 报告机制
- `matrix_projection` 尚未接入主训练链路

### 6.3 建议

`V3` 不要单独做成一套“旁路产品”，而是尽快抽象成：

- 主链路的质量判定插件
- 训练前数据过滤器
- 推荐后解释增强器
- QC 报告生成器

这样它的价值会比现在更大。

---

## 7. 优先级建议

### P0

1. 把 `V3` 的 `matrix_projection.json` 接入现有训练链路
2. 给 `mapped_chapter` 接入更真实的章节上下文来源
3. 为 `V3` 增加统一的离线评估与 QC 报告

### P1

4. 将 `reverse-outline / style DNA / checkpoint` 接入 `V2 Workbench`
5. 把核心推荐链路与质量层输出统一成一个标准决策对象
6. 拆分测试层级，减少碎片化回归成本

### P2

7. 收敛实验文档与临时产物，建立“主线 / 实验 / 归档”三级目录治理
8. 做更明确的角色化产品设计
9. 补齐反馈闭环和审计能力

---

## 8. 给 Codex 的直接结论

如果把这个项目交给 Codex 继续推进，最合理的策略不是“再加更多实验”，而是：

- **优先统一主链路和质量层**
- **把 `V3` 变成可插拔质量模块**
- **把评估体系从局部测试升级为统一 QC**
- **把产品形态从原型面板升级为可审计工作台**

一句话总结：

> `alpha-autopilot` 已经拥有一个不错的研究型底座，现在最重要的是把“能跑”升级成“能稳定判、能解释、能回归、能接主链路”。
