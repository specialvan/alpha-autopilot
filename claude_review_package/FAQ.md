# 常见问题 FAQ

## 1. 新需求来了，第一步做什么？

先不要改代码，先填写 `new_requirement_intake_template.md`，把层级、影响面、验收标准、测试门禁和回滚方案补齐。

## 2. 什么情况下只更新局部文档？

当需求不改变主线定义，只影响明确的增量内容时，通常只需要更新：

- `PROJECT_STATUS.md`
- `V2/frontend_PROJECT_STATUS.md`
- 对应阶段任务文档
- 对应增量说明文档

## 3. 什么情况下需要重收敛主线文档？

当需求会影响以下任一项时，需要重收敛主线文档：

- 主线边界
- `v2` / `v3` 关系
- schema / 接口契约
- 路线图阶段定义
- 状态文档与主线口径一致性

需要更新的通常包括：

- `CODEX_DEVELOPMENT_GOVERNANCE.md`
- `MASTER_ROADMAP.md`
- `README.md`
- `README_FOR_CODEX.md`
- `final_document_index.md`

## 4. 什么情况下必须先补测试？

只要有代码改动，就必须先考虑测试。最少规则是：

- 小改动补单元测试
- 跨模块改动补集成测试
- 影响旧功能补回归测试
- 面向交付补验收测试

## 5. 什么情况下必须写回滚？

只要需求会进执行，就必须写回滚信息。回滚至少要说明：

- 触发条件
- 关闭方式
- 回退方式
- 数据兼容方式
- 回滚后怎么验证恢复正常

## 6. 新能力默认放哪里？

默认放到 `Increment`，也就是 `v3` 增量层。

如果它只是探索性验证、还不能稳定交付，就放到 `Experimental`。

## 7. `v3` 会替代 `v2` 吗？

不会。当前治理口径里：

- `v2` 是主工作台和主交互入口
- `v3` 是质量层和推荐增强层

`v3` 是增强，不是替代。

## 8. 什么情况下必须更新状态文档？

只要需求已经明确归属某一层，并且不再只是讨论阶段，就应该更新：

- `PROJECT_STATUS.md`
- `V2/frontend_PROJECT_STATUS.md`
- 相关阶段任务文档

## 9. 什么情况下必须回滚？

优先回滚的情况包括：

- 破坏 Baseline
- 默认路径异常
- 新能力导致旧功能不稳定
- 增量接入后无法关闭或降级

## 10. 什么叫执行治理？

执行治理就是规定：

- 谁来做
- 按什么顺序做
- 先做什么后做什么
- 什么时候算完成
- 出问题怎么退回

它管的是开发过程，不是单独的代码细节。

## 11. 什么叫测试治理？

测试治理就是规定：

- 用什么测试证明没有改坏
- 用什么测试证明新功能有效
- 哪些测试是门禁
- 哪些测试是回归要求

它管的是“改得对不对”。

## 12. 什么叫归档？

归档是把已经被新主线覆盖、或者已经不再作为默认执行输入的历史材料移出主视图。

归档后只在需要追溯历史时读取。

## 13. Codex 默认应该先读哪些文档？

默认优先读：

- `CODEX_DEVELOPMENT_GOVERNANCE.md`
- `README_FOR_CODEX.md`
- `codex_run_card.md`
- `final_document_index.md`
- `new_requirement_intake_template.md`
- `new_requirement_execution_flow.md`

然后再看主线文档。

## 14. 如果文档之间有冲突怎么办？

按这个顺序裁决：

1. 治理规范
2. 执行流程
3. 接入模板和任务模板
4. 状态文档
5. 评审和历史材料

局部文档不能反向覆盖主线定义。

## 15. 一句话总结

> 新需求先判层级，改动先看边界，执行先补测试和回滚，文档冲突先按治理文档裁决。
