# Codex 开发进程治理规范

## 1. 治理目标

本规范用于管理 `alpha-autopilot` 后续由 Codex 驱动的开发进程，确保：

- `v1/v2` 作为稳定基线保持收口
- `v3` 作为增量需求独立推进
- 实验性探索与主线开发严格隔离
- 需求、实现、评审、回滚都有明确门禁
- 文档、代码、测试、状态三者始终对齐

## 2. 分层定义

### 2.1 Baseline Layer

`v1/v2` 属于基线层，原则上只允许：

- bug fix
- 安全修复
- 兼容性修补
- 与稳定性相关的必要维护

禁止在基线层继续扩展新的大功能。

### 2.2 Increment Layer

`v3` 属于增量层，所有新功能都应优先进入该层：

- 质量层增强
- 逆向拆解能力
- corpus QC
- 训练链路增强
- 解释性增强

增量层必须具备可独立关闭、可回滚、可灰度的条件。

### 2.3 Experimental Layer

实验层仅用于探索：

- 新算法
- 新 prompt 策略
- 新拆解方法
- 新评估器
- 新数据结构候选

实验层不得直接影响主链路默认行为。

## 3. Codex 工作模式

### 3.1 默认规则

Codex 后续开发必须遵循：

1. 先确认当前变更属于哪一层
2. 先看是否会破坏基线
3. 优先做最小改动
4. 所有新功能先进入增量层或实验层
5. 不允许在未定义门禁时直接改主线

### 3.2 任务优先级

优先级顺序如下：

1. 基线 bug fix
2. 基线稳定性修补
3. `v3` 增量功能
4. 实验性探索
5. 文档重构与归档

### 3.3 单次开发范围

Codex 每次只应处理一个清晰目标：

- 一个阶段任务
- 一个功能模块
- 一组强关联文件

避免跨层级、跨阶段同时扩张。

## 4. 需求接入门禁

### 4.1 进入 `v3` 的条件

一个需求只有在满足以下条件时，才允许进入 `v3`：

- 能明确提升推荐、解释或质量判断能力
- 不需要破坏当前基线接口
- 可定义离线评估方式
- 可定义回滚方式
- 可写入阶段路线图

### 4.2 进入实验层的条件

以下情况应先进入实验层：

- 方案不确定
- 指标不清晰
- 数据不足
- 可能需要多轮试验
- 可能要替换已有核心方案

### 4.3 禁止直接进入基线层的内容

以下内容不得直接写入 `v1/v2` 基线：

- 大型重构
- 新产品形态
- 新数据契约破坏性变更
- 无评估的策略替换
- 无回滚路径的链路替换

## 5. 退出与验收门禁

### 5.1 增量层退出条件

一个 `v3` 需求只有在满足以下条件时，才算可进入主线候选：

- 已完成代码实现，且默认关闭或灰度受控
- 已满足本节定义的测试、评估、回滚、影响面记录、文档同步要求

#### 5.1.1 必过测试类型

- 变更直接影响模块的单元测试必须全部通过。
- 变更涉及的主链路集成测试必须全部通过。
- 基线路径回归测试必须全部通过，不能因 `v3` 接入破坏 `v1/v2` 默认行为。
- 涉及数据契约、prompt、评估器、推荐/排序/判断策略变更时，必须补跑对应离线评估。
- 涉及 feature flag、配置切换、迁移脚本、回滚脚本时，必须验证开启和关闭两条路径都可执行。

#### 5.1.2 最低通过标准

- 本次变更定义的必跑测试项通过率必须为 `100%`，不得带已知失败项进入主线候选。
- 新增或本次变更直接影响的必跑测试，不允许以 `skip`、`xfail`、手工口头说明替代通过结果。
- 离线评估必须使用已登记的固定评估集；未登记评估集前，不得申报主线候选。
- 离线评估至少要记录 `1` 个核心效果指标和 `1` 个守护指标（如稳定性、耗时、资源消耗、误判率）；守护指标相对当前基线不得退化。
- 如果本次变更宣称“效果提升”，则必须在对应需求文档中预先写明目标指标和最小提升阈值；未写阈值或未达到阈值，均不得进入主线候选。

#### 5.1.3 回滚要求

- 每个 `v3` 变更必须提供单独回滚路径，优先级依次为：`feature flag 关闭`、`配置回切`、`模块回退`、`数据回退脚本`。
- 回滚步骤必须写成可执行清单，步骤数不得超过 `5` 步，且不得依赖临时人工排查。
- 涉及数据结构、数据契约、索引、迁移脚本的变更，必须同时提供逆向脚本或兼容期方案；没有逆向方案不得进入主线候选。
- 回滚后必须至少重新验证一次基线路径 smoke/回归测试，确认 `v1/v2` 可恢复到默认稳定状态。

#### 5.1.4 影响面记录要求

- 每个主线候选必须附带影响面记录，至少覆盖：变更模块、暴露接口、数据契约、配置项、上下游依赖、默认行为变化、监控指标、责任人。
- 影响面记录必须明确标注 `是否影响 baseline 默认路径`、`是否影响已有文档承诺`、`是否需要灰度` 三项结论。
- 任何一项影响面记录缺失，或责任人未明确，不得进入主线候选。

#### 5.1.5 文档同步要求

- `MASTER_ROADMAP.md` 必须同步该需求的层级归属、阶段位置、进入主线候选的判定结果。
- `PROJECT_STATUS.md` 或 `V2/frontend_PROJECT_STATUS.md` 必须同步真实完成状态、测试结果、离线评估结果、回滚状态，不得只写“已完成”。
- `PRD.md` 或 `V2/frontend_PRD.md` 在需求边界、验收标准、默认开关状态发生变化时必须同步更新。
- `V2/SECOND_PHASE_TASKS.md`、`THIRD_PHASE_TASKS.md` 在任务拆分、完成粒度、剩余风险发生变化时必须同步更新。
- 文档未同步完成前，变更只能停留在增量层，不得标记为主线候选。

### 5.2 主线接入条件

进入主线前还需满足：

- 已完整满足 `5.1` 的全部退出条件，且证据可追溯。
- 影响面评估已归档，兼容性结论已明确，未留空白风险项。
- 主线守护指标相对当前基线不得退化；若存在灰度方案，必须先给出放量条件和回退触发条件。
- 可观测性必须覆盖至少 `1` 个成功指标、`1` 个失败指标、`1` 个回滚触发信号。
- 责任边界必须明确到具体 owner；未指定 owner 的变更不得进入主线。

## 6. 回滚规则

### 6.1 回滚优先级

如果 `v3` 变更造成问题，回滚优先级如下：

1. 关闭 feature flag
2. 切回基线默认路径
3. 回退增量模块
4. 回退相关数据契约变更
5. 最后才考虑重做方案

### 6.2 回滚原则

- 回滚必须快于修复
- 回滚必须不依赖人工复杂操作
- 回滚后基线必须仍可正常运行

## 7. 文档治理规则

### 7.1 唯一总纲

`MASTER_ROADMAP.md` 应作为唯一总纲。

### 7.2 状态文档职责

`PROJECT_STATUS.md` 与 `V2/frontend_PROJECT_STATUS.md` 只记录真实状态，不重新定义路线。

### 7.3 需求文档职责

`PRD.md`、`V2/frontend_PRD.md` 只描述当前层的需求，不混写未来演进。

### 7.4 任务文档职责

`V2/SECOND_PHASE_TASKS.md`、`THIRD_PHASE_TASKS.md` 只做阶段执行拆分，不承担总路线定义。

### 7.5 评审文档职责

`*_REVIEW_*` 文档只做审计与结论，不修改需求边界。

### 7.6 文档冲突裁决优先级

文档内容发生冲突时，按以下优先级裁决，序号越小优先级越高：

1. `CODEX_DEVELOPMENT_GOVERNANCE.md`：定义分层规则、接入门禁、退出门禁、文档职责。
2. `MASTER_ROADMAP.md`：定义项目总路线、阶段顺序、需求所处分层。
3. `PRD.md`、`V2/frontend_PRD.md`：定义当前层的需求边界、验收标准、非功能约束。
4. `V2/SECOND_PHASE_TASKS.md`、`THIRD_PHASE_TASKS.md`：定义阶段执行拆分和交付顺序。
5. `PROJECT_STATUS.md`、`V2/frontend_PROJECT_STATUS.md`：只记录真实状态与时间点，不得反向改写路线、范围、门禁。
6. `*_REVIEW_*`：只记录审计发现、风险结论、准入建议，不得反向修改上位文档。

裁决执行规则如下：

- 下位文档与上位文档冲突时，以上位文档为准，下位文档必须在同一轮交付中修正。
- `PROJECT_STATUS.md` 与实现状态不一致时，以代码、测试结果、评估结果为准，并立即回写状态文档。
- `*_REVIEW_*` 可阻止接入，但不能单独扩大需求范围、改写路线层级或豁免门禁。
- 存在未裁决的文档冲突时，该需求不得进入主线候选。

## 8. 变更审查清单

Codex 在做任何实质性开发前，应先确认以下问题：

- 这次变更属于 baseline、increment 还是 experiment？
- 是否会影响当前稳定接口？
- 是否有测试覆盖？
- 是否有回滚方式？
- 是否已更新对应状态文档？
- 是否会让 `v3` 被误解成新主线？

## 9. 推荐的开发节奏

### 每次迭代

1. 定义单一目标
2. 归类层级
3. 修改最少文件
4. 补测试
5. 更新状态
6. 评估是否可进入下一步

### 每个阶段

1. 先锁定基线
2. 再推进 `v3`
3. 最后做实验探索

## 10. 当前执行建议

当前最适合推进的顺序是：

1. 收敛文档口径，明确基线 / 增量 / 实验三层结构
2. 将 `v3` 的接入门禁写入总路线图与阶段路线图
3. 让 `PROJECT_STATUS.md` 区分“能力完成”和“链路完成”
4. 为 `v3` 增量功能建立可回滚开关与评估集
5. 再进入下一轮 Codex 实现

## 11. 一句话治理原则

> 基线稳定收口，增量独立推进，实验严格隔离，所有变更先评估、再实现、后接入。
