# Codex 开发进程治理规范

## 1. 治理目标

本规范用于管理 `alpha-autopilot` 后续由 Codex 驱动的开发进程，确保：

- `v1/v2` 作为稳定基线保持收口
- `v3` 作为增量需求独立推进
- 实验性探索与主线开发严格隔离
- 需求、实现、评审、回滚都有明确门禁
- 文档、代码、测试、状态三者始终对齐

## 2. 分层定义

### 2.1 Baseline Layer

`v1/v2` 属于基线层，原则上只允许：

- bug fix
- 安全修复
- 兼容性修补
- 与稳定性相关的必要维护

禁止在基线层继续扩展新的大功能。

### 2.2 Increment Layer

`v3` 属于增量层，所有新功能都应优先进入该层：

- 质量层增强
- 逆向拆解能力
- corpus QC
- 训练链路增强
- 解释性增强

增量层必须具备可独立关闭、可回滚、可灰度的条件。

### 2.3 Experimental Layer

实验层仅用于探索：

- 新算法
- 新 prompt 策略
- 新拆解方法
- 新评估器
- 新数据结构候选

实验层不得直接影响主链路默认行为。

## 3. Codex 工作模式

### 3.1 默认规则

Codex 后续开发必须遵循：

1. 先确认当前变更属于哪一层
2. 先看是否会破坏基线
3. 优先做最小改动
4. 所有新功能先进入增量层或实验层
5. 不允许在未定义门禁时直接改主线

### 3.2 任务优先级

优先级顺序如下：

1. 基线 bug fix
2. 基线稳定性修补
3. `v3` 增量功能
4. 实验性探索
5. 文档重构与归档

### 3.3 单次开发范围

Codex 每次只应处理一个清晰目标：

- 一个阶段任务
- 一个功能模块
- 一组强关联文件

避免跨层级、跨阶段同时扩张。

## 4. 需求接入门禁

### 4.1 进入 `v3` 的条件

一个需求只有在满足以下条件时，才允许进入 `v3`：

- 能明确提升推荐、解释或质量判断能力
- 不需要破坏当前基线接口
- 可定义离线评估方式
- 可定义回滚方式
- 可写入阶段路线图

### 4.2 进入实验层的条件

以下情况应先进入实验层：

- 方案不确定
- 指标不清晰
- 数据不足
- 可能需要多轮试验
- 可能要替换已有核心方案

### 4.3 禁止直接进入基线层的内容

以下内容不得直接写入 `v1/v2` 基线：

- 大型重构
- 新产品形态
- 新数据契约破坏性变更
- 无评估的策略替换
- 无回滚路径的链路替换

## 5. 退出与验收门禁

### 5.1 增量层退出条件

一个 `v3` 需求只有在满足以下条件时，才算可进入主线候选：

- 已完成代码实现
- 已完成单元/集成测试
- 已完成离线评估
- 已完成回归验证
- 已明确回滚方式
- 已在文档中标注完成粒度

### 5.2 主线接入条件

进入主线前还需满足：

- 影响面已评估
- 兼容性已确认
- 性能无明显退化
- 可观测性足够
- 责任边界清晰

## 6. 回滚规则

### 6.1 回滚优先级

如果 `v3` 变更造成问题，回滚优先级如下：

1. 关闭 feature flag
2. 切回基线默认路径
3. 回退增量模块
4. 回退相关数据契约变更
5. 最后才考虑重做方案

### 6.2 回滚原则

- 回滚必须快于修复
- 回滚必须不依赖人工复杂操作
- 回滚后基线必须仍可正常运行

## 7. 文档治理规则

### 7.1 唯一总纲

`MASTER_ROADMAP.md` 应作为唯一总纲。

### 7.2 状态文档职责

`PROJECT_STATUS.md` 与 `frontend_PROJECT_STATUS.md` 只记录真实状态，不重新定义路线。

### 7.3 需求文档职责

`PRD.md`、`frontend_PRD.md` 只描述当前层的需求，不混写未来演进。

### 7.4 任务文档职责

`SECOND_PHASE_TASKS.md`、`THIRD_PHASE_TASKS.md` 只做阶段执行拆分，不承担总路线定义。

### 7.5 评审文档职责

`*_REVIEW_*` 文档只做审计与结论，不修改需求边界。

## 8. 变更审查清单

Codex 在做任何实质性开发前，应先确认以下问题：

- 这次变更属于 baseline、increment 还是 experiment？
- 是否会影响当前稳定接口？
- 是否有测试覆盖？
- 是否有回滚方式？
- 是否已更新对应状态文档？
- 是否会让 `v3` 被误解成新主线？

## 9. 推荐的开发节奏

### 每次迭代

1. 定义单一目标
2. 归类层级
3. 修改最少文件
4. 补测试
5. 更新状态
6. 评估是否可进入下一步

### 每个阶段

1. 先锁定基线
2. 再推进 `v3`
3. 最后做实验探索

## 10. 当前执行建议

当前最适合推进的顺序是：

1. 收敛文档口径，明确基线 / 增量 / 实验三层结构
2. 将 `v3` 的接入门禁写入总路线图与阶段路线图
3. 让 `PROJECT_STATUS.md` 区分“能力完成”和“链路完成”
4. 为 `v3` 增量功能建立可回滚开关与评估集
5. 再进入下一轮 Codex 实现

## 11. 一句话治理原则

> 基线稳定收口，增量独立推进，实验严格隔离，所有变更先评估、再实现、后接入。
