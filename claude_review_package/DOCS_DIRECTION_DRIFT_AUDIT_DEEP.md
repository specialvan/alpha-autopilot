# 文档方向漂移深审计

## 审计结论

结论比上一版更严格一些：**总体方向仍然一致，但已经出现几处“口径漂移 / 叙述漂移 / 阶段边界漂移”的风险点**。这些风险点目前还没有演变成真正的方向错误，但如果继续叠加文档，未来很容易造成实现团队对主线目标的理解分叉。

换句话说，项目现在不是“跑偏”，而是处于“主线正确，但文档层开始变厚、口径开始分叉”的状态。

## 1. 审计范围

本次重点比对了以下文档：

- `README.md`
- `MASTER_ROADMAP.md`
- `THIRD_PHASE_ROADMAP.md`
- `PROJECT_STATUS.md`
- `frontend_PRD.md`
- `frontend_PROJECT_STATUS.md`
- `frontend_REVIEW_GUIDE.md`
- `frontend_DELIVERY_CHECKLIST.md`
- `TECH_BOTTLENECKS.md`

## 2. 明确一致的部分

### 2.1 总目标一致

所有文档都围绕同一件事展开：

- 小说章节推荐
- 写作辅助
- 可解释推荐
- 训练反馈闭环
- 工程可迭代性

这一点没有变。

### 2.2 `v2` / `v3` 的大方向一致

文档里对它们的定位基本稳定：

- `v2` 是工作台、推荐展示、交互入口
- `v3` 是逆向拆解、质量层、QC、训练增强

这部分没有根本冲突。

### 2.3 阶段总叙事一致

阶段主线基本统一为：

1. 原型闭环
2. 稳定化与扩展
3. 价值进化 / 质量层接入

因此从宏观路线看，文档没有分裂成两个产品。

## 3. 发现的漂移风险点

下面是更严格审计下需要重点关注的地方。

### 3.1 `README.md` 与后续阶段文档之间存在“成熟度口径漂移”

`README.md` 仍然把项目描述成：

- Python narrative recommendation prototype
- companion React dashboard
- demo API / prototype 视角

而后续文档已经进入：

- `V2 Workbench`
- `V3 Reverse Decomposition Quality Layer`
- corpus QC
- matrix projection 入链
- 质量层插件化

这不是目标冲突，但存在**读者误解风险**：

- 读 `README.md` 会觉得项目还停留在原型
- 读 `PROJECT_STATUS.md` 会觉得主链路已经较完整
- 读 `THIRD_PHASE_ROADMAP.md` 又会觉得已经进入质量层工程化

这说明项目对外的“成熟度叙事”不统一。

#### 建议

`README.md` 需要明确加入一句：

- 当前是研究型原型，但已经进入 `v2/v3` 分阶段建设
- `v2` 是工作台主线，`v3` 是质量层增强

否则 README 会长期落后于真实工程状态。

---

### 3.2 `TECH_BOTTLENECKS.md` 中“暂时保持原型独立”与总体路线存在轻微张力

文档里写到：

- 当前只是推荐原型，还未和小说生成器深度耦合
- 暂时保持原型独立
- 后续再决定是否接入更大工程

这和 `MASTER_ROADMAP.md` 中第二阶段、第三阶段关于“生成链路增强”“推荐结果转章节大纲”“摘要转章节结构模板”的方向并不冲突，但容易产生一个歧义：

> 到底是长期保持独立，还是明确走向生成链路融合？

当前总路线看，答案其实是：

- **短期保持推荐原型独立，优先保证可解释性和闭环稳定**
- **中长期要接入生成链路，形成写作辅助系统**

但这个分层没有在文档里写死，因此容易被误读成目标摇摆。

#### 建议

在 `TECH_BOTTLENECKS.md` 和总路线图里补充一句：

- “短期独立，长期耦合”

这样能消除“是不是不打算接生成器了”的疑问。

---

### 3.3 `frontend_PRD.md` 与 `frontend_PROJECT_STATUS.md` 的产品定义边界存在轻微漂移

`frontend_PRD.md` 强调的是：

- 量化式工作台
- 展示推荐、日志、版本、反馈、风险
- 偏工程交付界面

而 `frontend_PROJECT_STATUS.md` 已经把 `V2 Workbench` 定义为：

- 独立路由
- 决策驾驶舱
- 具备 compare/history
- 接入章节上下文

这说明前端已经从“展示型 dashboard”升级为“决策工作台”。

问题不在实现，而在文档语义：

- PRD 仍偏向静态展示工作台
- Status 已经偏向操作型、路由化、决策型工作台

这会造成后续开发时，团队对“前端到底是看板还是驾驶舱”的理解不统一。

#### 建议

把前端产品语言统一为：

- `dashboard` = 低交互总览
- `V2 Workbench` = 决策驾驶舱

不要把它们混成一个“前端工作台”概念。

---

### 3.4 `PROJECT_STATUS.md` 与 `THIRD_PHASE_ROADMAP.md` 之间有“已完成/待完成”边界要再收紧

`PROJECT_STATUS.md` 已明确说：

- `V3` taxonomy / schema 已完成
- `V3` pipeline 已完成
- `V3` PlotPilot import 已完成
- `V3` 本地构建脚本已完成

但 `THIRD_PHASE_ROADMAP.md` 又明确说：

- `matrix_projection.json` 尚未正式进入训练主循环
- `mapped_chapter` 不是完整章节 API
- 需要补 corpus QC

这不是冲突，但说明“完成”的定义只覆盖了**单点能力完成**，没有覆盖**链路接入完成**。

也就是说，文档里“已完成”的粒度与“阶段完成”的粒度不一致。

#### 建议

把状态分成两层：

- **能力完成**：某模块可运行
- **链路完成**：该模块已接入主线

例如：

- `V3 taxonomy`：能力完成
- `matrix_projection` 入训练：链路未完成

不然“已完成”三个字会误导人。

---

### 3.5 文档命名体系过于分散，容易掩盖主次关系

现在同时存在：

- `ROADMAP.md`
- `MASTER_ROADMAP.md`
- `SECOND_PHASE_TASKS.md`
- `THIRD_PHASE_TASKS.md`
- `PROJECT_STATUS.md`
- `frontend_PROJECT_STATUS.md`
- `frontend_PRD.md`
- `frontend_REVIEW_GUIDE.md`
- `TECH_BOTTLENECKS.md`
- `PRD.md`
- 大量 review / delivery / checklist 文档

这说明文档治理已经从“有内容”进入“有很多内容”。

风险是：

- 哪份是唯一总纲不够清晰
- 哪份是当前执行依据不够清晰
- 哪份只是历史归档不够清晰

这会导致方向漂移的表象，即使代码本身没漂。

#### 建议

明确三层：

1. **总纲**：唯一主路线图
2. **状态**：当前真实进度
3. **执行**：阶段任务与本次交付

其他文档必须标注属于哪一层。

## 4. 潜在的认知分叉点

下面不是当前冲突，而是未来最容易出问题的地方。

### 4.1 研究原型 vs 产品化系统

当前所有文档都还带“prototype”气质，但实现已经接近一个可持续迭代系统。

如果不统一术语，后续容易出现两种说法：

- “这只是研究原型，不用太严谨”
- “这已经是工作台和质量层系统了，应该按交付标准做”

建议统一口径为：

> 研究型系统，按产品级工程标准建设。

### 4.2 推荐系统 vs 写作辅助系统

总路线图里已经明确向写作辅助延展，但前端和后端的部分文档仍更像“推荐系统”。

这不是错，但如果长期不统一，会出现：

- 推荐侧强调排序
- 写作侧强调章节结构
- 质量层强调拆解

三者都对，但需要一句顶层定义把它们串起来。

### 4.3 `v3` 是增强层还是新主线

这是最重要的认知分叉点。

目前文档事实指向的是：

- `v3` 是主线增强层
- 不是独立产品线
- 不是替代 `v2`

但因为 `v3` 描述很完整，容易被写成“新系统”。

必须防止这件事。

### 5.3 推荐补充到 `PROJECT_STATUS.md`

- 将“已完成”拆成“能力完成 / 主链路接入完成”两列
- 避免把局部完成写成整体完成

### 5.4 推荐补充到 `TECH_BOTTLENECKS.md`

### 5.5 推荐补充到 `frontend_PRD.md`

- 明确 `dashboard` 和 `V2 Workbench` 的双层结构
- 避免前端产品定位模糊

## 6. 最终严格结论

### 是否漂移

**没有实质性方向漂移。**

### 是否存在口径风险

**有，而且已经开始显现。**

### 风险性质

不是代码方向错误，而是：

- 总纲更新速度跟不上实现速度
- 成熟度叙事不统一
- 能力完成与链路完成混写
- `v3` 容易被误解为独立主线

### 一句话判断

> 项目方向是对的，但文档体系已经进入“需要收敛口径，否则未来会制造方向漂移假象”的阶段。

## 7. 建议的下一步

如果你要继续推进，最优先的动作不是加新需求，而是做一次文档治理：

1. 选定唯一总纲文档
2. 明确 `v2` / `v3` 主次关系
3. 给每份文档打上层级标签
4. 把“能力完成”和“链路完成”分开写
5. 删除或归档旧口径文档

这样才能确保开发方向长期不漂。
