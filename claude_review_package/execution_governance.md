# 执行治理说明

## 1. 目的

执行治理用于规定：谁来做、按什么顺序做、做到什么算完成、出问题如何处理。

它管理的是开发过程，而不是单纯的代码内容。

## 2. 核心原则

- 一次只处理一个清晰目标
- 先判断任务属于 `Baseline`、`Increment` 还是 `Experimental`
- 先锁定影响面，再开始改动
- 每次变更后必须更新状态文档
- 任何新功能默认进入 `Increment`
- 实验性内容不得直接影响主线默认行为
- 所有结论都要能被文档、测试记录、日志、开关状态或回滚记录验证

## 3. 执行顺序

### 3.1 开始前

开始前必须补齐以下可验证字段，缺一项就不进入开发：

- `task_id`：任务编号或链接
- `owner`：当前执行人
- `layer`：`Baseline` / `Increment` / `Experimental`
- `scope`：本次只改哪些模块、文件或流程
- `impact_boundary`：会影响哪些状态、接口、主线流程
- `test_plan`：需要跑哪些测试，预期用什么方式验证
- `rollback_plan`：回滚或关闭方案是什么
- `evidence_source`：这些结论来自哪份文档、哪条需求或哪次评审

开始前的检查项：

1. 已阅读治理规范和工程包执行说明
2. 已确认任务层级与三层结构口径一致
3. 已确认是否会影响主线默认行为
4. 已确认是否需要测试、灰度、回滚或关闭开关
5. 已写清最小修改范围和验证方式

### 3.2 开发中

开发中必须持续维护以下可验证字段：

- `diff_scope`：当前实际修改范围
- `layer_guard`：是否仍然停留在已确认层级内
- `test_run`：已执行的测试命令、时间和结果
- `state_sync`：对应状态文档是否同步更新
- `open_risk`：当前仍未解决的风险和处理人

开发中的检查项：

1. 只做最小改动，不扩张到未确认范围
2. 不跨层级扩张，不把 Experimental 行为写成默认主线
3. 保持接口、状态、文档一致
4. 每次产生可验证结果后及时记录证据
5. 需要时先补测试，再继续后续改动

### 3.3 开发后

开发后必须补齐以下可验证字段：

- `dod_status`：是否满足完成定义
- `doc_updated`：对应状态文档是否已更新
- `risk_note`：残余风险是否已写明
- `rollback_ready`：回滚或关闭方式是否可执行
- `verification_artifact`：测试记录、截图、日志或链接

开发后的检查项：

1. 更新对应状态文档
2. 补充风险说明和边界说明
3. 如有必要，更新路线图或任务文档
4. 确认回滚、关闭或降级路径可执行
5. 确认结果能被独立复核

## 4. 任务边界

### Baseline 任务

适合：
- 修复 bug
- 兼容性调整
- 稳定性修补

要求：
- 不改变主线定义
- 不引入新主流程
- 验证重点是已有行为是否保持不变
- 回滚重点是恢复到原有主线状态

### Increment 任务

适合：
- `v3` 质量层
- 推荐增强
- 评估增强
- 工作台增强

要求：
- 可灰度
- 可回滚
- 可单独关闭
- 必须写明开关、入口或降级路径
- 验证重点是可控发布和可控退出

### Experimental 任务

适合：
- 候选方案
- 试验性实现
- 未冻结的探索

要求：
- 不污染主线
- 不作为默认行为
- 必须说明隔离边界和退出方式
- 验证重点是实验可观察，但不外溢到主线

## 5. 完成标准

一个任务只有在同时满足以下条件时，才算执行完成：

- 实现已完成，且修改范围与开始前确认一致
- 相关测试已通过，或测试未执行的原因已明确记录
- 对应文档已更新，且内容能对应到实际变更
- 影响边界已明确，且没有越过已确认层级
- 回滚、关闭或降级方式已写明，并可实际执行
- 证据可复核：至少能从文档、测试、日志或状态记录中找到对应项

分层完成定义补充：

- `Baseline`：不改变主线定义，不引入新主流程，验证结果不显示主线回归
- `Increment`：灰度、回滚、单独关闭路径都已验证可用
- `Experimental`：未进入默认行为，不影响主线默认路径，隔离边界清楚

## 6. 失败处理

如果执行中出现以下任一可观测条件，立即触发停止扩张：

1. 构建失败、单测失败、集成测试失败或关键校验失败
2. 变更范围超出已确认 `scope` 或越过已确认 `layer`
3. 出现与本次任务相关的新增错误日志、异常堆栈、报警或断言失败
4. 预期验证结果与实际结果不一致
5. `Increment` 的开关、灰度或关闭路径不可用
6. `Experimental` 行为开始影响主线默认路径

处理顺序保持不变：

1. 先停止扩张
2. 先确认是否属于层级判断错误
3. 先回到最小范围修正
4. 必要时回滚到可运行状态
5. 再继续下一步

触发标准要求：

- 触发条件必须能被测试结果、日志、报警、开关状态或回滚记录直接证明
- 如果没有提前写明阈值，则默认以“出现失败、异常、回归或无法验证”为触发依据
- 任何不能复核的“感觉不对”不算完成，但可以作为进一步排查信号

## 7. 与文档和测试的关系

- 文档治理回答“应该做什么”
- 代码治理回答“改了什么”
- 测试治理回答“改得对不对”
- 执行治理回答“按什么步骤改，谁负责，何时收口”

## 8. 一句话原则

> 先定层级，再定边界；先做最小改动，再补测试，再更新状态，最后确认可回滚。
