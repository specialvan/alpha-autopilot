# 执行治理说明

## 1. 目的

执行治理用于规定：谁来做、按什么顺序做、做到什么算完成、出问题如何处理。

它管理的是开发过程，而不是单纯的代码内容。

## 2. 核心原则

- 一次只处理一个清晰目标
- 先判断任务属于 `Baseline`、`Increment` 还是 `Experimental`
- 先锁定影响面，再开始改动
- 每次变更后必须更新状态文档
- 任何新功能默认进入 `Increment`
- 实验性内容不得直接影响主线默认行为

## 3. 执行顺序

### 3.1 开始前

1. 阅读治理规范
2. 阅读工程包执行说明
3. 确认任务层级
4. 确认是否需要测试和回滚
5. 确认这次任务是否会影响主线

### 3.2 开发中

1. 做最小改动
2. 避免跨层级扩张
3. 保持接口和状态一致
4. 需要时同步补测试

### 3.3 开发后

1. 更新对应状态文档
2. 补充风险说明
3. 如有必要，更新路线图或任务文档
4. 确认能回滚

## 4. 任务边界

### Baseline 任务

适合：
- 修复 bug
- 兼容性调整
- 稳定性修补

要求：
- 不改变主线定义
- 不引入新主流程

### Increment 任务

适合：
- `v3` 质量层
- 推荐增强
- 评估增强
- 工作台增强

要求：
- 可灰度
- 可回滚
- 可单独关闭

### Experimental 任务

适合：
- 候选方案
- 试验性实现
- 未冻结的探索

要求：
- 不污染主线
- 不作为默认行为

## 5. 完成标准

一个任务只有在同时满足以下条件时，才算执行完成：

- 实现已完成
- 相关测试已通过或有明确说明
- 对应文档已更新
- 影响边界已明确
- 必要时回滚方式已写明

## 6. 失败处理

如果执行中发现偏离：

1. 先停止扩张
2. 先确认是否属于层级判断错误
3. 先回到最小范围修正
4. 必要时回滚到可运行状态
5. 再继续下一步

## 7. 与文档和测试的关系

- 文档治理回答“应该做什么”
- 代码治理回答“改了什么”
- 测试治理回答“改得对不对”
- 执行治理回答“按什么步骤改，谁负责，何时收口”

## 8. 一句话原则

> 先定层级，再定边界；先做最小改动，再补测试，再更新状态，最后确认可回滚。
