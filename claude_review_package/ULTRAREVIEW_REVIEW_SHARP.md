# alpha-autopilot Review

> 评审对象：`D:\workspace\alpha-autopilot`
>
> 评审目标：以 PR review 的口吻，直说问题、指出风险、给出可执行修正建议。

## 总评

这个仓库已经不是一个“能跑的 demo”了，但也还远没到“可以放心作为统一主线”的程度。

它现在最大的问题不是功能少，而是**实验层、主链路、质量层、产品层混在一起，边界不够硬**。代码、测试、文档、导入资产都在往前推进，但系统层面还没有形成一个真正统一的决策闭环。

如果只看成果数量，这个项目很强；如果看架构收敛度和长期维护性，目前仍然偏散。

综合评价：**7.8 / 10**。

---

## 你已经做对的部分

### 1. 主链路基本完整

推荐、训练、日志、版本、前端工作台、API 都已经有了，说明不是“拼接式样板”，而是有真实闭环的。

### 2. 可解释性方向是对的

feature matrix、versioning、training log、heuristic decomposition、evidence span 这些设计都对叙事类系统很关键。至少方向没有跑偏。

### 3. `V3` 不是空想

`V3` 已经有 taxonomy / schema / pipeline / import / projection，这说明你不是在讲概念，而是在做可落地的质量层实验。

---

## 主要问题

### 1. 主链路和质量层仍然是两套系统

这是当前最核心的问题。

`V3` 现在像一个旁路实验层，而不是主链路的一部分。它能产出结果，但这些结果没有被统一地接进训练、排序、推荐解释和回归验证中。

后果是：

- 主链路继续跑，但质量层收益无法系统化沉淀
- 质量层看起来很强，但很难证明它真的提升了最终推荐质量
- 后续会越来越像“多套能力并存”，而不是“一套系统收敛”

这不是小问题，是架构收敛失败的前兆。

### 2. 数据接入还不够真实

文档里已经写明，`mapped_chapter` 目前优先使用聚合上下文和导入夹具，不是完整真实章节 API。

这意味着当前验证更多是在“受控样本环境”里成立，而不是在真实数据流里成立。

如果这个状态持续太久，会出现两个风险：

- 以为系统稳定，其实只是 fixtures 稳定
- 真实输入稍微复杂一点，边界问题就会暴露

### 3. 测试覆盖有，但还不成体系

测试数量不少，这是优点；但从结构看，测试更像是围着功能点补出来的，而不是按系统边界组织的。

建议你尽快把测试重新分层，不然后面会越来越难维护：

- 核心推荐回归
- 质量层回归
- API contract tests
- 前端页面 / 组件 tests
- 导入脚本 sanity tests

否则测试会变成“越来越多，但越来越难信任”。

### 4. 仓库里的阶段性产物太多

现在仓库里有大量 delivery report、plan、review、spec、checklist、half-progress 之类的文件。

这说明过程记录很勤奋，但也意味着：

- 信息密度开始过载
- 新人很难判断哪些是主线、哪些是历史记录、哪些是临时实验
- 真实需要维护的关键文档会被淹没

如果不收敛，文档本身会成为维护负担。

### 5. 产品角色还没想清楚

当前产品体验偏研究员 / 开发者视角，离明确的业务角色还有差距。

至少要回答这些问题：

- 谁在用它？作者、编辑、运营还是分析人员？
- 他们分别需要看到什么？
- 什么叫一次“成功推荐”？
- 什么叫“不可接受的推荐”？

现在这些还没有被产品化。

## 代码层面的直接判断

### 好的地方

- 模块拆分总体清楚
- 业务对象和评估对象有一定边界
- 前后端分离明确
- 说明性文档比一般原型项目完整很多

### 要警惕的地方

- 实验代码继续膨胀，主入口会越来越乱
- 质量层如果继续独立演进，最终会变成第二套产品
- 配置、样本、导入资产如果没有严格分级，后面会很难管

---

## `V3` 专项结论

`V3` 是这份仓库里最值得继续推进的方向，但前提是它必须从“实验成果”变成“系统能力”。

现在它的问题不是没价值，而是**价值没有被接进主系统**。

### 你应该马上做的事情

1. 把 `matrix_projection.json` 接入训练主链路
2. 把 `V3` 输出统一成标准决策对象
3. 把 `V3` 做成可插拔质量模块，而不是旁路报告生成器
4. 加一层统一 QC，而不是继续加零散测试

### 不建议继续做的事情

- 再造一套平行的实验入口
- 再堆更多一次性报告
- 再增加不能回流主链路的分析产物

---

## 优先级建议

### P0

- 接通 `V3` 与主训练链路
- 让 `mapped_chapter` 走真实章节来源
- 建立统一离线 QC / admission 评估

### P1

- 将 `reverse-outline / style DNA / checkpoint` 接入 `V2 Workbench`
- 统一推荐结果、解释结果和质量层结果的数据结构
- 重构测试分层

### P2

- 收敛文档和临时产物
- 设计更明确的用户角色
- 补反馈闭环和审计能力

---

## 结论

这个项目现在不是“缺能力”，而是“缺收敛”。

你已经把原型做到了一个很不错的阶段，下一步最重要的不是继续扩张，而是把系统打磨成一个能稳定运行、稳定解释、稳定回归的统一主线。

一句话建议：

> 停止继续堆旁路实验，把 `V3`、推荐主链路、测试体系和工作台统一成一套可审计的决策系统。
