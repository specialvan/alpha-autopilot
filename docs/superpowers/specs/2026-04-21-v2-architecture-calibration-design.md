# alpha-autopilot V2 架构校准式重构设计

**日期**: 2026-04-21

## 1. 背景与问题定义

`alpha-autopilot` 当前最关键的问题，不是缺少更多 feature，也不是单纯工程稳定性不足，而是顶层抽象定义已经发生漂移：

- 原始立项目标是把“象棋启发式搜索 + 特征矩阵评估”的核心思想迁移为“受规则约束的章节推进推荐系统”
- 当前实现和文档逐渐收缩为“候选动作打分排序器”
- 第二阶段稳定化和第三阶段价值进化需求被提前混入第一阶段，导致阶段边界失真
- 如果继续在现有抽象上叠加能力，后续会出现状态模型、候选动作、反馈指标、接口契约和验证口径同时返工

因此，本次工作的目标不是继续扩展功能，而是将项目打回第一阶段目标，执行一次受控的“架构校准式重构”。

## 2. 目标

本次 `v2` 设计的目标只有三个：

1. 重新冻结小说章节推荐系统的顶层抽象
2. 在仓内并行建立可验证的 `v2` 最小闭环
3. 在不破坏 `v1` 最小 MVP 的前提下，为后续合入建立明确闸门

## 3. 非目标

本次设计明确不包含以下内容：

- 不在 `v2` 中合入第三阶段“推荐价值自适应进化”
- 不在 `v2` 中提前落地 `v3` 新功能、新模型能力、新题材扩展需求
- 不做整仓 Big Bang Rewrite
- 不要求 `v2` 第一版就默认启用复杂多步搜索
- 不以“看起来更智能”替代正式验证

## 4. 方法论定位

本次 `v2` 校准采用的是一组组合式工程模式，而不是单一模式：

- `Strangler Fig Pattern`
  - 在仓内并行建立 `v2`，通过后逐步替换 `v1` 默认入口
- `Branch by Abstraction`
  - 先冻结抽象和契约，再允许新旧实现并行
- `Anti-Corruption Layer`
  - 通过新命名空间和适配层隔离 `v1` 已漂移的实现与契约污染
- `Golden Master / Specification by Example`
  - 通过 golden cases、rule fixtures、evaluation ledger 固定边界与验收口径

本项目的工程定位可表述为：

> 基于 Strangler Fig 的并行替换式架构校准重构

## 5. 版本语义与阶段边界

### 5.1 v1

`v1` 是当前可运行原型，进入冻结模式。

职责：

- 保留最小 MVP
- 修复阻塞运行的 bug
- 作为 `v2` 的对照基线

禁止：

- 新增 feature
- 修改模型能力
- 混入新抽象

### 5.2 v2

`v2` 是第一阶段回炉重构线。

职责：

- 重建顶层抽象
- 重新定义规则层、搜索层、评价闭环、验证口径
- 重建第一阶段所需的最小闭环

目标：

- 不是先追求更强
- 而是先追求更正确、更稳、更可验证

### 5.3 v3

`v3` 只作为后续路线图与需求池存在。

职责：

- 承接第二阶段稳定化
- 承接第三阶段价值进化
- 承接新功能、新模型能力、新题材泛化需求

约束：

- `v3` 当前不落代码
- 只有 `v2` 合入并稳定后才允许启动

## 6. v2 顶层抽象定义

`v2` 不再以“章节推荐器 / 特征打分器”直接起手，而是固定四层核心抽象。

### 6.1 规则层 Rule Layer

职责：

- 定义在当前故事状态下，哪些推进动作合法
- 定义哪些动作不合法
- 定义哪些动作前提不足但理论可执行

输出：

- 合法动作集合
- 每个动作的前置条件命中情况
- 风险标记
- 禁止原因

本层等价于棋类系统中的“合法走法生成”，但这里的对象是叙事动作，而不是棋步。

### 6.2 搜索层 Search Layer

职责：

- 在合法动作集合上执行推演
- 比较不同推进路径的阶段性收益
- 为后续多步 lookahead 保留扩展位

分层约束：

- `v2.0` 基线：支持单步搜索接口
- `v2.1+` 才允许真正多步 lookahead 成为默认能力

该约束的目的，是先保证抽象正确，再扩展搜索复杂度。

### 6.3 评价层 Evaluation Layer

职责：

- 对动作或动作路径进行分维度打分
- 输出可解释的推荐原因
- 支持反馈后的权重调整和版本比较

评价对象：

- 不是章节文本质量本身
- 而是“当前推荐动作对叙事推进的预期价值”

至少包含以下维度：

- 结构价值
- 连续性安全
- 情绪/爽点回报
- 伏笔与回收平衡
- 题材/阶段适配度

### 6.4 验证层 Validation Layer

职责：

- 验证系统是否真的实现了“受规则约束的可推演推荐”
- 验证特征矩阵方案是否可以替代一部分数据库/提示经验
- 为合入评审提供稳定、可回放、可比较的依据

本层不是运行时主链路的一部分，但必须在 `v2` 一开始就冻结。

## 7. 命名、契约与隔离原则

`v2` 可以复用稳定的领域命名，但不得复用 `v1` 中语义已漂移的核心实现、模块路径与数据契约。

允许：

- 继续使用稳定领域名词，例如 `StoryState`、`NarrativeAction`、`RecommendationResult`
- 在新的 `v2` 命名空间中重新定义这些类型

禁止：

- `v2` 直接 import `v1` 的核心领域类型
- 在 `v1` 原模块路径内就地改语义
- 用旧契约承载新抽象

该原则的目的是避免“旧壳套新逻辑”。

## 8. 仓内并行目录策略

为避免污染当前运行中的 `v1`，`v2` 采用仓内并行结构。

建议目录：

- `alpha_autopilot_v2/`
  - 承载 `v2` 领域核心
- `backend/app/services/narrative_v2/`
  - 承载 API 到 `v2` 核心的薄适配层
- `artifacts/v2/`
  - 存放 `v2` 快照、ledger、基准输出
- `docs/superpowers/specs/`
  - 存放本次设计文档
- `docs/architecture/v2/` 或后续同级目录
  - 存放 `v2` 详细抽象、验证、切换文档

建议的 `alpha_autopilot_v2/` 内部边界：

- `domain/`
  - `StoryState`
  - `NarrativeAction`
  - `RuleCheck`
  - `RecommendationResult`
- `rules/`
  - 合法动作判定
  - 前提约束
  - 禁止原因
- `search/`
  - 单步推演
  - 多步扩展位
- `evaluation/`
  - 分维度打分
  - 解释输出
- `feedback/`
  - 反馈记录模型
  - 版本化评价闭环
- `validation/`
  - golden cases
  - rule fixtures
  - ledger 读写

## 9. 验证资产冻结

为防止后续再次以主观感受替代评审，`v2` 必须引入三类固定验证资产。

### 9.1 golden cases

内容：

- 少量高代表性的故事状态输入
- 对应期望输出边界
- Top-K 推荐范围
- 解释字段要求

作用：

- 冻结推荐行为边界
- 防止重构后结果漂移不可追溯

### 9.2 rule fixtures

内容：

- 动作合法性样例
- 前提缺失样例
- 禁止原因样例

作用：

- 冻结规则层判断标准
- 防止所有动作都退化为“只打分不判定”

### 9.3 evaluation ledger

内容：

- 每次版本在基准样例上的结果记录
- 分维度评分
- 规则判断
- 版本差异

作用：

- 支持回放
- 支持比较
- 支持审计

## 10. 验收与合入闸门

`v2` 必须同时通过两个层级的验收，才有资格进入替换评审。

### 10.1 抽象校准验收

用于判断顶层定义是否成立。

必须同时满足：

- 规则层能区分 `合法 / 不合法 / 前提不足`
- 搜索层在接口上支持单步推演，并保留多步扩展位
- 评价层输出分维度解释，而不是单一黑盒总分
- 验证层能对同一输入给出稳定、可复盘的判断记录

若以上四项任一不成立，则 `v2` 视为抽象校准失败，不进入替换评审。

### 10.2 MVP 可替换验收

用于判断 `v2` 是否有资格接替 `v1`。

必须同时满足：

- 对同一组基准样例，`v2` 能稳定输出 Top-K 推荐与解释字段
- `v2` 不低于 `v1` 的最小可运行能力：训练、推荐、反馈记录、版本快照
- 文档、接口、样例三者一致
- `v1` 在切换前持续保持独立可运行

## 11. 切换策略

切换必须分阶段进行，而不是直接替换默认入口。

顺序如下：

1. 保持 `v1` 默认入口不变
2. 为 `v2` 建立平行入口，例如独立 service、独立 API prefix 或独立 CLI
3. 先完成规则、搜索、评价、验证四层的抽象校准
4. 再完成 API 对齐和最小闭环联调
5. 最后才进入替换评审

替换当天的约束：

- 默认入口切换后，仍保留 `v1` 回退入口
- 至少保留一个完整评审周期
- 未通过稳定性复核前，不删除 `v1`

## 12. 替代数据库的验证口径

“特征矩阵是否可以替代海量数据库”在本项目中只能作为研究性假设，不得直接写成既定结论。

`v2` 冻结后的验证口径应为：

- 验证特征矩阵 + 规则约束 + 状态推演，是否能替代一部分静态经验库与手工提示经验
- 不验证“完全替代数据库”
- 不验证“完全替代大模型生成经验”
- 不以单次样例效果作为路线成立依据

可接受的验证结论只有三类：

- `成立`
  - 在基准样例集上，`v2` 形成稳定、可解释、可回放的推荐闭环
- `部分成立`
  - 可替代部分经验表达，但仍需数据库或生成系统辅助
- `不成立`
  - 无法形成稳定推荐或验证资产无法支撑路线结论

## 13. 反模式清单

以下行为在 `v2` 中应视为明确反模式：

- 在 `v1` 原有目录中直接就地改语义
- 未冻结验证口径就继续叠加功能
- 把 `v3` 能力提前混入 `v2`
- 以演示效果替代抽象校准
- 以总分排序替代规则判定
- 把多步搜索承诺写进 PRD，却只交付单步打分器且不标注差异

## 14. 结论

本设计确定项目后续采用以下路线：

- `v1` 冻结保底
- `v2` 仓内并行，执行第一阶段回炉与架构校准
- `v3` 暂不落代码，仅作为未来路线图存在

只有当 `v2` 同时通过抽象校准验收和 MVP 可替换验收后，才允许启动默认入口替换评审。
